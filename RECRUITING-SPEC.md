## 0. What this tab is

The Recruiting tab is a fourth entry in the ULRG sub-tab strip:
`Overview | Scorecard | Recruiting | <team rooms>` (`frontend/src/ulrg/UlrgTabs.jsx`). It lives
under the `ulrg` tab grant, like Scorecard. It has three jobs:

1. **Actionable.** A daily *Do next* queue, generated by rules. Each row can be acted on from the
   row itself: text, call, email or book. Those actions write back to GHL.
2. **Accountable.** Pace to the monthly goal per person, weekly commitments that roll into the L10
   Scorecard, and a Team Leader leaderboard.
3. **Automated.** Plain rules configured in Settings build the queue, and those same rules clear
   it when GHL shows the work happened.

**Roles in this tab:**
- **Owner:** sees everything, plus source attribution.
- **Team Leader (×3):** closes recruits in appointments and owns candidates from *Met* onward.
- **SDR (×1):** books appointments onto Team Leader calendars and owns candidates up to and
  including *Appointment set*.

## 1. Audit — what exists today, and what it means for this build

### 1.1 The GHL client is read-only

`backend/app/integrations/ghl.py` has these functions: `get_contacts`, `get_custom_fields`,
`get_opportunity`, `get_users`, `get_pipelines`, `get_opportunities`, `get_subscriptions`,
`ghl_transactions`, `get_invoices` and `ghl_subscription_detail`. The file has no POST, PUT or
PATCH. Other details:
- Auth is a Private Integration Token (PIT), stored Fernet-encrypted in
  `Integration.access_token_enc`.
- `Version: 2021-07-28` is pinned in `GHL_VERSION`.
- `_headers()` sends no `Content-Type`, so every write needs it added.

**This tab will be the first GHL write path in the product.** The nearest precedents are:
- **Books:** `BOOKS_WRITEBACK_ENABLED`, with the rule that Claude never posts to QuickBooks.
- **AI Employees:** `AI_EMPLOYEES_WRITEBACK_ENABLED` plus a per-employee `writeback_enabled` flag.
  Both must be open (`services/ai_employees.writeback_open`), and a closed gate returns 409.

Recruiting writes follow the same double gate (§5.2).

### 1.2 GHL data is a snapshot with no history

`services/sync._ghl_snapshot` **replaces** a kind's row set on every sync.
`services/ads_funnel.py` already records the consequence: GHL fields are current state, not
history. Sales Desk solved the same problem with an append-only log (`SalesCall` +
`SalesCallChange`, models.py:1930): "the tab is computed from this log, never from live GHL
fields".

Recruiting needs history for stage durations, "signed this month", speed to lead and show rate,
so it needs its own append-only tables (§4). It must not reuse `MetricRecord(kind="recruiting")`.
The Forum's funnel uses that kind as a current-state count, and `_ghl_snapshot` would wipe it.

### 1.3 Provider key: add `ghl_recruiting`, do not reuse `ghl`

- `sync.run_one` dispatches on `integ.provider`, and `"ghl"` runs `sync_ghl`, which is
  membership-specific (tags, renewals and sales pipelines).
- `create_integration` looks rows up by `(provider, business_id)`.

A `ghl` row on the ULRG business would therefore run the membership sync against the brokerage's
location. So:
- Add a provider `ghl_recruiting`, bound to the `real_estate` business
  (`roles.real_estate(s, tenant_id)`).
- It joins the existing **Go High Level** family row in Settings › Integrations. The family
  grouping from INTEGRATIONS-SPEC §1.2 already supports several providers per vendor.

Touch points, each of which already has a guard test:
- `routers/integrations.create_integration`: provider allow-list.
- `plans._CORE_SOURCES`
- `services/integrations_view`: `ORDER`, `FAMILY`, `CATEGORY`, `META`, `CONNECTABLE_KIND`.
- `frontend/src/Settings.jsx`: `DESC`, `MONO` and `SAMPLE_VIEW` (keep the sample payload in step
  with the real one).
- `tests/test_provider_ui_is_complete.py`
- `sync.run_one` dispatch: a new `elif integ.provider == "ghl_recruiting"` branch.

### 1.4 Where ULRG lives

- Production ULRG is the `utah-life` tenant. Its Follow Up Boss connection feeds the portal's
  *Needs You Today* (FUB-FOLLOW-UPS-SPEC). The dev seed and `validate_ulrg_resolvers.py` use
  `springb`.
- **Recruiting lives in GHL.** Agent follow-ups stay in FUB, and the two queues must not merge.
- The sourcing doc (`docs/ulrg-scorecard-sourcing.md`) still lists "Confirm whether recruiting
  lives in a GHL pipeline" as open. Phase 0 closes it.

### 1.5 Roles and identity

`User.role` is `owner | admin | member`, and tab access comes from `services/tabs.py`. Nothing
models Team Leader or SDR. The roster (`IntranetMember`) and `services/member_identity.matches_for`
already match a person to FUB and Sisu identities by email. Extend that to GHL users:
- `get_users` returns `{id, name, email}`.
- Match by email, with an override on the recruiting seat (§4.1). This avoids FUB-SPEC finding
  A7, where agent matching could not be fixed from the UI.

## 4. Data model (new tables, one migration per phase)

All tables are tenant-scoped and use `GUID()` ids. None of them replace GHL rows wholesale.

### 4.1 `recruiting_seat` (Phase 1)
Who does what. Editable in Settings › Recruiting.

| column | type | note |
|---|---|---|
| id, tenant_id, business_id | GUID | business = `roles.real_estate` |
| user_id | GUID null | Axcion user, when they have a login |
| member_id | GUID null | `IntranetMember`, for identity matching |
| role | str(16) | `team_leader \| sdr` (owner/admin come from `User.role`) |
| display_name, title | str | "Team Leader · Draper" |
| ghl_user_id | str(64) null | matched by email from `get_users`; override here |
| calendar_id | str(64) null | Team Leader's recruiting calendar (D4) |
| from_number | str(20) null | SMS sender (D5), E.164 |
| writeback_enabled | bool default false | per-seat gate (§5.2) |
| active | bool | soft delete |

### 4.2 `recruiting_candidate` (Phase 1)
Current state, **upserted by `(tenant_id, opportunity_id)`**. Never delete-and-replace.

`opportunity_id`, `contact_id`, `pipeline_id`, `stage_id`, `stage_group`, `status`
(open/won/lost/abandoned), `owner_seat_id` (from `assignedTo` → seat), `booker_seat_id`,
`name`, `brokerage`, `city`, `source` (`attributionSource` / `source`), `gci_ttm` (from a
production custom field, D2), `entered_stage_at`, `created_at_src`, `updated_at_src`,
`last_outbound_at`, `last_inbound_at`, `dnd` (json of per-channel DND), `source_url`.

### 4.3 `recruiting_stage_event` (Phase 1), append-only
Written when a sync sees `stage_id` change, and when **we** move a stage (§5.4).

`candidate_id`, `from_stage_id`, `to_stage_id`, `to_group`, `occurred_at`, `source`
(`sync|axcion|webhook`), `actor_seat_id`. "Signed in September" is this table filtered to
`to_group = 'Signed'`. It is never inferred from current state.

### 4.4 `recruiting_appointment` (Phase 1)
Upserted by GHL `event id`: `calendar_id`, `seat_id` (Team Leader), `candidate_id`, `start_at`,
`status` (`new|confirmed|showed|noshow|cancelled|…`), `created_at_src`, `booked_by_seat_id`,
`source` (`axcion|ghl`). The Booked, Held and show-rate figures, and the "Booked this week, by
calendar" strip, come from here.

### 4.5 `recruiting_activity` (Phase 1 read, Phase 4 write), append-only
One row per touch: `kind` (`sms_out|sms_in|email_out|email_in|call_out|call_in|note|task|booking|stage_move`),
`candidate_id`, `seat_id`, `occurred_at`, `ghl_message_id` / `ghl_note_id` / `ghl_task_id` /
`ghl_event_id`, `duration_s` (calls), `summary` (≤ 280 chars, no full bodies of inbound
messages), `source` (`axcion|ghl_poll|webhook`). This is also the dedupe spine: a message we sent
comes back through the poll carrying the same `ghl_message_id`.

### 4.6 `recruiting_action` (Phase 4), the write outbox
One row per write attempt. See §5.3 for the lifecycle.

`id`, `idempotency_key` (unique per tenant), `seat_id`, `actor_user_id`, `candidate_id`,
`queue_item_id`, `kind` (`send_sms|send_email|add_note|upsert_task|complete_task|move_stage|book|log_call`),
`request` (json, **redacted**: no token, message body kept for audit), `status`
(`queued|sending|sent|failed|refused|dry_run`), `attempts`, `next_attempt_at`, `ghl_ref`,
`http_status`, `error`, `created_at`, `sent_at`.

### 4.7 `recruiting_queue_item` (Phase 3)
Built by the rule engine. The key is `(tenant_id, rule_key, candidate_id, window_key)`, so
re-running a rule is idempotent.

`state` (`open|done|snoozed|auto_cleared|expired`), `due_at`, `why` (rendered server-side),
`primary_action`, `owner_seat_id`, `cleared_by` (`user|action|rule`), `cleared_at`,
`snoozed_until`, `action_id`.

### 4.8 `recruiting_commitment` (Phase 5)
`seat_id`, `week_start` (Monday, business-local), `metric`
(`held|offers|booked|dials|convos`), `commit`. Actuals are never stored here. They're computed
from 4.3–4.5 so they can't drift.

### 4.9 Configuration (no table)
`Integration(provider="ghl_recruiting").config` holds the settings below. The Settings › Recruiting
screen reads and writes them through a `clean_settings(raw, strict=)` function, on the bounded
pattern in `follow_ups.py`.
- `location_id`, `pipeline_id`
- `recruiting_stage_groups`: `[label, owner_role, [stage_ids]]`
- `gci_field_id`, `brokerage_field_id`
- `rules` (§6)
- `templates` (plain text with `{first}`, `{owner_first}` and `{calendar_owner}` merge fields)
- `quiet_hours` (default 08:00–21:00 local)
- `writeback_enabled`
- `dry_run`

## 5. Write-back to GHL — the mechanics

### 5.1 Auth and scopes

- **Keep the Private Integration Token.** HighLevel positions PITs for internal, single
  sub-account use, including internal data sync, custom reporting dashboards and automated tasks.
  It reserves OAuth for public apps and anything that needs webhooks, custom modules or custom
  conversation providers. Two consequences follow:
  - **No webhooks** (§5.6).
  - **No "external outbound call" logging**: `POST /conversations/messages/outbound` requires a
    `conversationProviderId`, which only a marketplace app can own (§5.4, calls).
- The ULRG location needs a **new PIT** created by a location admin with the scopes below. The
  Spring B tokens are unrelated. **VERIFY** each name in the PIT scope picker during Phase 0, and
  record the final list in `docs/recruiting-sourcing.md`.

| Scope | For |
|---|---|
| `contacts.readonly`, `contacts.write` | contact reads; notes and tasks (`/contacts/{id}/notes`, `/contacts/{id}/tasks`) |
| `opportunities.readonly`, `opportunities.write` | pipeline reads; stage moves |
| `conversations.readonly`, `conversations/message.readonly` | activity, replies, calls (Phase 6 poll) |
| `conversations/message.write` | send SMS / email |
| `calendars.readonly`, `calendars/events.readonly`, `calendars/events.write` | calendars, free slots, create/update appointments |
| `users.readonly` | seat ↔ GHL user matching |
| `locations.readonly`, `locations/customFields.readonly` | location timezone, custom field definitions |

- **Least privilege:** Phase 1 ships with only the read scopes. The token is re-issued with write
  scopes at Phase 4. A `403` on a write surfaces as "This connection is missing
  `<scope>`. An admin can add it to the GHL private integration." It must never look like a
  generic failure.

### 5.2 Gates (all four must be open, or the write is refused with a reason)

1. `settings.RECRUITING_WRITEBACK_ENABLED` (env, default False). Declare it in `config.py` and
   list it in the operator console flags (`routers/platform.py`, like
   `AI_EMPLOYEES_WRITEBACK_ENABLED`).
2. `integration.config.writeback_enabled` (workspace, set by owner/admin).
3. `recruiting_seat.writeback_enabled` (per person, so the rollout can go seat by seat).
4. The workspace is not suspended and not `syncs_frozen`.

`connection.writeback` in the payload tells the UI which gate is closed. The drawer's send button
then reads "Sending is off for this workspace", not a dead button.

`config.dry_run = true` runs the whole pipeline and stores `status="dry_run"` with the exact
request body, **without calling GHL**. Phase 4 runs a week in dry run.

### 5.3 The outbox (every write goes through it)

```
POST /ulrg/recruiting/actions  { idempotency_key, kind, candidate_id, queue_item_id?, payload }
  1. auth: viewer can act on this candidate (owner/admin, or owner_seat, or SDR for SDR-stage candidates)
  2. gates (§5.2) → 409 with reason
  3. compliance (§5.5) → 422 with reason, action row status="refused"
  4. INSERT recruiting_action(status="queued") ON CONFLICT(idempotency_key) → return the existing row
  5. audit(category="Recruiting", action="recruiting.<kind>", target=candidate)
  6. commit, then execute inline with an 8 s budget:
       sending → call GHL → sent (store ghl_ref) | failed
     429 / 5xx / timeout → status="queued", next_attempt_at = backoff; the user sees "Queued, will retry"
  7. on sent: write recruiting_activity; apply side effects (stage_event, queue item → done, next step task)
  8. return { status, ghl_ref, activity }
```

- **Idempotency.** The client generates `idempotency_key` (a UUID) per click, so a double-click or
  a retried request cannot send two texts. For SMS/email there is no GHL-side idempotency, so the
  outbox is the only guard. A row stuck in `sending` for more than 2 min is **not** auto-retried.
  It goes to `failed` with "Unknown outcome, check GHL before resending", because a duplicate text
  to a recruit is worse than a missing one.
- **Retry worker.** `recruiting_outbox_tick` runs every minute (add it to `jobs.catalog`). It
  drains `queued` rows whose `next_attempt_at` has passed. Backoff is 30 s, 2 m, then 10 m, with a
  maximum of 3 attempts, after which the row goes to `failed`. A 4xx other than 429 is never
  retried.
- **Rate limits.** HighLevel's published limits are **100 requests per 10 s and 200,000 per day,
  per app per location**. Every response carries `X-RateLimit-Remaining`,
  `X-RateLimit-Daily-Remaining`, `X-RateLimit-Max` and `X-RateLimit-Interval-Milliseconds`.
  - The docs describe these for OAuth apps. **VERIFY** that PIT calls return the same headers.
  - Sync and writes share one budget per location. Add a small async token bucket in
    `integrations/ghl.py`, keyed by `location_id`, that reads those headers.
  - **Writes take priority:** a sync backs off when `Remaining < 20`, and writes proceed down to
    `Remaining < 5`.
  - Add `ghl_request()`, a single `httpx` wrapper that does headers, Content-Type, the bucket,
    retry on 429/5xx (the pattern already in `get_opportunity`) and error mapping (§5.7). Migrate
    the read functions onto it in the same phase.

### 5.4 Each write, endpoint by endpoint

Base `https://services.leadconnectorhq.com`, headers `Authorization: Bearer <PIT>`,
`Version: 2021-07-28`, `Content-Type: application/json`, `Accept: application/json`.

**Send SMS / email** — `POST /conversations/messages`
```json
{ "type": "SMS", "contactId": "<contact>", "message": "<text>", "fromNumber": "<seat.from_number?>", "toNumber": "<E.164?>" }
{ "type": "Email", "contactId": "<contact>", "subject": "…", "html": "<p>…</p>", "message": "<plain>",
  "emailFrom": "<seat email?>", "emailReplyMode": "reply", "threadId": "<last email thread?>" }
```
- The response carries `conversationId` and `messageId`, plus `emailMessageId` for email. Store
  `messageId` on the activity row.
- The response means *queued*, not delivered. Delivery status arrives through the Phase 6 poll.
- `scheduledTimestamp` (UTC seconds) exists. Use it to hold a send inside quiet hours instead of
  refusing, and store the scheduled time. **VERIFY** it with the probe.
- The docs mark `status` as required in the v3 schema. **VERIFY** whether `2021-07-28` requires it.
- Attribution: the send body has a `userId` only for `InternalComment`, so an SMS may show as sent
  by the API user in GHL. Also write a note (`POST /contacts/{id}/notes` with `userId =
  seat.ghl_user_id`) *only if* the probe shows the message is unattributed. Don't double-log by
  default.

**Log a call** (no API dialing; see the constraints above)
- The **Call** button opens the dialer:
  - `tel:<phone>` on mobile
  - the GHL contact page (`ghl.contact_url`) on desktop, where the user's LC Phone dialer is
- When the user logs the outcome in the drawer (Connected / Left voicemail / No answer, plus an
  optional note), we:
  - `POST /contacts/{contactId}/notes` `{ "body": "Call · Connected · <note>", "userId": "<seat.ghl_user_id>" }`
  - write `recruiting_activity(kind="call_out", source="axcion")`
- Calls placed natively in GHL also appear through the Phase 6 conversations poll (message type
  call, with duration). The poll is what counts **Dials** and **Conversations** for the SDR card:
  a logged outcome is not a dial count. If a call arrives from both paths within 10 min, dedupe
  them.

**Next step / due** — contact tasks
- Create: `POST /contacts/{contactId}/tasks` `{ "title", "body", "dueDate": "<ISO>", "completed": false, "assignedTo": "<ghl_user_id>" }`
- Update: `PUT /contacts/{contactId}/tasks/{taskId}`
- Complete: `PUT /contacts/{contactId}/tasks/{taskId}/completed` `{ "completed": true }`
- The drawer's *Next step* input debounces for 800 ms and upserts **one open "Recruiting next
  step" task per candidate** (`ghl_task_id` is stored on the candidate).
- Changing the due chip updates `dueDate`. Clearing a queue item by action completes that task.

**Move stage** — `PUT /opportunities/{opportunityId}` `{ "pipelineStageId": "<id>" }`
- Also `status: "won"` when the target group is *Signed*, and `"abandoned"` for Nurture if D2 says
  so.
- **Optimistic-concurrency check:**
  1. Before writing, `GET /opportunities/{id}` (already `get_opportunity`) and compare
     `pipelineStageId` and `updatedAt` with what the drawer showed.
  2. If they differ, return 409 "Moved in GHL to <stage> 4 min ago" and refresh the drawer.
- On success, write `recruiting_stage_event(source="axcion")`, update the candidate row, and
  re-evaluate that candidate's queue items.

**Book** — free slots, then create appointment
1. `GET /calendars/{calendarId}/free-slots?startDate=<ms>&endDate=<ms>&timezone=America/Denver`
   (add `userId` for round-robin calendars, D4).
   - Cache for 60 s per calendar.
   - This feeds "Where to book", open-slot counts, and "Next up" (the Team Leader with the most
     open slots in the next 5 business days, tie-broken by fewest bookings this week).
   - **VERIFY** the parameter names and the response shape (it's keyed by date).
2. `POST /calendars/events/appointments`:
   ```json
   { "calendarId": "<TL calendar>", "locationId": "<loc>", "contactId": "<contact>",
     "startTime": "2026-09-24T09:00:00-06:00", "endTime": "…+45m",
     "title": "Recruiting · <candidate> with <TL first>", "appointmentStatus": "confirmed",
     "assignedUserId": "<TL ghl_user_id>", "address": "<office>", "toNotify": true }
   ```
   - `toNotify: true` lets the location's own confirmation and reminder automations fire, so we
     don't send a second invite. The drawer copy ("The invite goes out by text and email") is
     only true if D-check confirms those automations exist. Otherwise follow up with a
     `send_sms`.
   - Never set `ignoreFreeSlotValidation` or `ignoreDateRange`. A slot taken since the list loaded
     must fail with "That time was just taken" and refresh the slots.
3. On success:
   - upsert `recruiting_appointment(source="axcion", booked_by_seat_id=<actor>)`
   - move the opportunity to the *Appointment set* stage if it's earlier than that
   - set the next step to "Meet <TL> <slot>"
   - clear the queue item
   - update the candidate's `owner_seat_id` to the Team Leader **only** when D2's hand-off rule
     says the Team Leader owns from *Appointment set* (the design says *Met*, so ownership
     transfers on the held appointment, not on booking)

**Update appointment status** (Team Leader marks held or no-show from Axcion, optional):
`PUT /calendars/events/appointments/{eventId}` `{ "appointmentStatus": "showed|noshow" }`.

### 5.5 Compliance — enforced server-side, before the outbox

- **DND.** Read `contact.dnd` and `contact.dndSettings.{SMS,Email,Call}.status` from the synced
  candidate (and re-read on send if the candidate row is more than 10 min old).
  - Refuse with "Brandon has opted out of texts".
  - Never offer an override.
- **Quiet hours.** Recruit-local is unknown, so use the location timezone: 08:00–21:00. Outside
  that, offer "Send at 8:00 am" (using `scheduledTimestamp`) instead of sending. This is a
  TCPA-motivated default, and it isn't configurable below 08:00 or above 21:00.
- **A2P 10DLC.** SMS writes stay off until D6 is confirmed. On the first send attempt, GHL returns
  an error if the number isn't registered. Map it to "This number isn't registered for business
  texting yet" (§5.7).
- **No AI drafting.** Drafts are the plain templates in `config.templates`. The user asked for
  rules, not an AI employee. The `why` line is rendered from structured facts, not generated.
- **PII.** Store message summaries of 280 characters or fewer, not inbound bodies. Keep the full
  text of what *we* sent in `recruiting_action.request` for audit. Retain it for 365 days, in line
  with `RECALL_TRANSCRIPT_RETAIN_DAYS`, and purge it in the outbox tick.

### 5.6 Reading back what happened (PITs have no webhooks)

- **6a — Poll (default).** `recruiting_activity_tick` runs every 5 minutes, on the
  `fub_followups_tick` pattern. It runs only after one full sync has succeeded and never alongside
  a running sync.
  - `GET /conversations/search?locationId=…&sort=desc&sortBy=last_message_date&limit=100`, paging
    until `last_message_date < cursor`. Filter to recruiting contacts.
  - For each changed conversation, `GET /conversations/{id}/messages` since the cursor.
  - Upsert `recruiting_activity` by `ghl_message_id`. Set `last_inbound_at`/`last_outbound_at` and
    the delivery status of our sends.
  - `GET /calendars/events?locationId=…&calendarId=<each TL>&startTime=<ms>&endTime=<ms>` over
    −14 d to +30 d picks up statuses (`showed`/`noshow`) and bookings made in GHL directly.
  - Cost: about 1 + N(changed) + 3 requests per 5 minutes, well inside 100 per 10 s.
  - **VERIFY** the search params and the message type values (`TYPE_SMS`, `TYPE_CALL`, …) with the
    probe.
- **6b — GHL Workflow webhook (optional, lower latency).**
  - A location admin builds a GHL Workflow: trigger *Customer Replied* / *Appointment Status* /
    *Pipeline Stage Changed*, action *Webhook* → `POST /api/v1/webhooks/ghl-recruiting`.
  - It sends the header `X-Axcion-Secret: <per-integration secret>` (stored `enc()`, rotated from
    Settings).
  - The payload is treated only as a **hint**: the handler re-reads the contact/opportunity
    through the API before writing anything, so a forged or stale body can't change state. The
    raw body is never trusted.
  - Follow the `routers/recall.py` webhook pattern: a secret gate, 200 for an unknown id (no retry
    storm), idempotent handling.
- **6c — Marketplace OAuth app (later).** It unlocks signed native webhooks and a custom
  conversation provider, so calls can be logged as real call messages. OAuth tokens expire every
  24 h and refresh tokens rotate, so this needs the refresh plumbing QBO already has
  (`refresh_token_enc`, `token_expires_at`). It's out of scope for this build.

### 5.7 Error mapping (one table, in `ghl_request`)

| GHL | Meaning | Integration status | User sees |
|---|---|---|---|
| 401 | token revoked / wrong | `error` + `last_error` | "The GHL connection needs to be reconnected" (owners get Settings link) |
| 403 | scope missing | unchanged | "This connection is missing <scope>" |
| 404 | contact/opp/calendar gone | unchanged | "Not found in GHL. It may have been deleted." + refresh candidate |
| 409/422 slot | slot taken | unchanged | "That time was just taken" + refreshed slots |
| 422 other | validation | unchanged | GHL's `message` verbatim, owners only; others "GHL refused this, details logged" |
| 429 | rate limited | unchanged | "Queued, will retry" |
| 5xx / timeout | GHL down | unchanged | "Queued, will retry" |

## 6. The rule engine (Settings › Recruiting › Rules, not on the tab)

The user removed the Rules card from the tab. Rules are configured in Settings only.

`services/recruiting_rules.py` works like `follow_ups.py`:
- `DEFAULTS`, `BOUNDS`, `clean_settings(raw, strict)` and pure functions, with no HTTP.
- `recruiting_queue_tick` runs every 5 minutes, and also at 06:00 business-local as the
  "morning build".
- Each rule yields `(rule_key, candidate_id, window_key, owner_seat_id, due_at, why, primary_action)`
  from the local tables only.
- It upserts `recruiting_queue_item`. Items whose condition no longer holds become
  `auto_cleared`, with `cleared_by="rule"`. That's how "sending clears it" works even when the
  send happened in GHL.

| key | Default condition | Owner | Primary | Auto-clears when |
|---|---|---|---|---|
| `new_lead_untouched` | candidate created ≥ 60 min ago, no outbound activity | SDR (unassigned → SDR) | text | any outbound |
| `appt_24h` | appointment starts in 18–30 h, status ≠ confirmed-by-reply | appointment's Team Leader | text | inbound reply or status confirmed |
| `met_no_next_step` | in *Met* group ≥ 48 h, no open next-step task and no future appointment | Team Leader | email | task created / appointment booked / stage moved |
| `offer_out_stale` | in *Offer out* ≥ 5 d, no inbound in 5 d | Team Leader (copy owner) | call | inbound or stage moved |
| `no_touch_7d` | open, not nurture, no activity 7 d | stage owner | text | any activity |
| `stage_14d` | same stage ≥ 14 d | stage owner | call | stage moved |
| `appt_set_no_event` | in *Appointment set* ≥ 24 h, no future appointment | SDR | book | appointment exists |
| `signed` | stage → Signed | none (no queue item) | none | writes stage_event, triggers the Scorecard resolver |

- **Bounds:** the minutes and days are editable within bounds; stage groups are picked from the
  location's real stages (the `stages_in_use` pattern).
- **Due labels** ("20 hrs late", "Today", "Tomorrow") are rendered server-side in business-local
  time.
- **Snooze** sets `snoozed_until` to the next business day at 06:00.
- **Done** marks the item `done` and completes its GHL task if one exists. That's a write, so it
  goes through the outbox and falls back to local-only when writeback is closed.
- The "Tomorrow" button in the UI is snooze.

## 7. Metric definitions (server-side, one function each, unit-tested)

| Metric | Definition |
|---|---|
| Signed (period) | distinct candidates with a `stage_event` into group *Signed* in the period, attributed to `owner_seat_id` at the time of the event |
| Pace | `signed / elapsed_fraction`, where `elapsed_fraction = business days elapsed / business days in period` (weekday count; D7 can add holidays). Verdict uses the Scorecard verdict rules, not a new vocabulary |
| Need | `goal − signed` |
| Path | open candidates in groups *Offer out* then *Met*, ordered by group then days in stage. The line is chosen from the four cases in the design (§3 `path.line`) |
| Booked (SDR) | `recruiting_appointment` rows with `booked_by_seat_id = SDR` and `created_at_src` in the period (week or month) |
| Held | appointments with status `showed` in the period, **or** a stage_event into *Met* with no matching appointment (D8), deduped per candidate per day |
| Show rate | held ÷ (booked appointments whose `start_at` has passed in the period and whose status is final) |
| Dials / Conversations | SDR `call_out` activities today; conversations = calls ≥ 60 s + inbound replies (D9) |
| Speed to lead | median minutes from `created_at_src` to first outbound activity, for candidates created this month. A candidate with no touch yet counts as *now − created* |
| Close rate (90 d) | signed ÷ held for each Team Leader, over a rolling 90 days |
| Commitment band | `actual / (commit × week_elapsed)` × 100 → `band()`. `week_elapsed` = business day of week ÷ 5 (Wednesday = 0.6) |
| Stuck | open candidates with days in stage ≥ 7 |
| Conversion arrow | 90-day share of candidates who entered a group and later entered the next group |
